  <strong>A native, pathlib-inspired filesystem API for TypeScript, Bun, Node and Rust.</strong><br/>

> [!IMPORTANT]
> **pathway is in Phase 1.** The workspace, the three-crate split, the pixi/turbo
> orchestration, CI, the offline sandbox and the docs site are real. The engine is
> **scaffold**: `crates/core`'s modules are declared with the specs they will be built
> from, `WalkIterator` is a stub, and the N-API bridge exports only `engineVersion()`
> and `napiVersion()`. All three crates are `publish = false` until the crates.io names
> are reserved — see [`backlog/docs/phase-plan.md`](backlog/docs/phase-plan.md), Phase 1 Step 0.

## 🖥️ Platform Support

The badge above mirrors `[workspace] platforms` in `pixi.toml`. The *development* platform
and the *target* platform are tracked separately: a contributor needs the pixi environment,
whereas a consumer only needs the addon npm resolves for their machine.

| Platform | Development | Published addon | Notes |
|----------|-------------|-----------------|-------|
| `linux-64` | ✅ supported | 🟡 planned | The only entry in `[workspace] platforms`; `sandbox/developer-linux-64` is the packed offline transport |
| `osx-arm64`, `osx-64` | 🟡 untested | 🟡 planned | `scripts/restore.sh` maps the triples, but no bundle is published and no runner has proved the airlock |
| `win32-x64-msvc` | ❌ not supported | 🟡 planned | `conda-forge` has no `bun` build, so Windows is out of `[workspace] platforms` |

The platform `optionalDependencies` matrix is generated by `napi publish` at release time
and is never hand-maintained. Consumers need **Node ≥ 24** (`engines` in
`packages/path/package.json`); Bun 1.3/1.4 is supported through the same Node-API ABI.

## 📦 Architecture

```text
   TypeScript surface                        Rust surface
   ──────────────────                        ────────────
  ┌───────────────────────────┐        ┌───────────────────────────┐
  │ @archont561/pathway       │        │ pathway-fs                │
  │ packages/path             │        │ crates/path               │
  │                           │        │                           │
  │ Path · Serializer<T>      │        │ Path · walk builder       │
  │ walkFiles · FileSystem    │        │ serde sugar               │
  │ string ops stay in `pathe`│        │ std::path semantics       │
  └─────────────┬─────────────┘        └─────────────┬─────────────┘
                │                                    │
      napi-rs   │  coarse-grained boundary           │  plain Rust
                │  (bulk ops only)                   │
  ┌─────────────▼─────────────┐                      │
  │ pathway-fs-engine         │                      │
  │ crates/engine  · cdylib   │  glue only           │
  │ npm-only, never crates.io │                      │
  └─────────────┬─────────────┘                      │
                │                                    │
  ┌─────────────▼────────────────────────────────────▼─────────────┐
  │ pathway-fs-core · crates/core · rlib, zero napi dependencies   │
  │ fused walk · hashing · codecs · atomic IO · sandbox · locking  │
  │ `cargo test -p pathway-fs-core` runs with no Node in the loop  │
  └────────────────────────────────────────────────────────────────┘
```

Both surfaces are **thin**. A rule implemented in a surface instead of in the core is a bug:
the two are meant to agree, and a difference between them is not a feature.

## 🚀 Key Features

| Icon | Feature | Status | Description |
|------|---------|--------|-------------|
| ⚡ | **Fused Walk** | 🟡 planned | Traversal + `stat` + content hash + glob/regex filtering in one syscall pass — the defensible moat |
| 🚧 | **Coarse-Grained FFI** | ✅ enforced | The boundary is for bulk work only; `join()` never crosses it |
| 🦀 | **Dual Surface, One Engine** | ✅ scaffolded | `@archont561/pathway` on npm and `pathway-fs` on crates.io over the same `pathway-fs-core` |
| 🔌 | **Pluggable Serializers** | 🟡 partial | `Serializer<T>` passed in, not selected by string; per-`FileSystem` registry, never global |
| 🔒 | **OS-Level Primitives** | 🟡 planned | `flock()`/`LockFileEx`, `O_TMPFILE`, `openat(O_NOFOLLOW)` sandboxing, native watching |
| 📦 | **Offline Sandbox** | ✅ proven | `pixi-sandbox` orphan-branch transport; `cargo build --offline` from a vendored tree |
| 🔁 | **One Task Graph** | ✅ proven | pixi exposes repo-wide verbs; turbo runs them across both languages with one cache |
| 📚 | **Knowledge Base** | ✅ active | `.knowledge/` is an Open Knowledge Format bundle and the source of design truth |

## ⚡ Quick Start

Requires [Pixi](https://pixi.sh) ≥ 0.81. Nothing else — no system Rust, no Node, no Bun.

```bash
git clone https://github.com/Archont561/pathway && cd pathway

pixi run hooks-install   # lefthook git hooks, once per clone
pixi run build           # the native addon, the TypeScript packages, the docs site
pixi run gates           # everything that must pass before a push
pixi run dev             # the documentation site, live
```

### Restoring on an airlocked machine

The toolchain is packed onto an orphan branch, so a disconnected host needs no network:

```bash
git fetch origin '+refs/heads/sandbox/*:refs/remotes/origin/sandbox/*'
sh scripts/restore.sh

pixi install --frozen --offline            # must be a no-op
pixi run -e default cargo build --offline  # uses the restored vendor tree
```

`scripts/restore.sh` resolves `<branch_prefix>/<bundle>-<platform>` from `.pixi-sandbox.toml`
— the same plan the publisher uses — so a renamed bundle needs no edited script.
`PIXI_SANDBOX_BRANCH` pins an exact branch; `PIXI_SANDBOX_BUNDLE` picks one when several
cover the platform.

> [!TIP]
> If `restore.sh` reports `fatal: not a valid object name: origin/sandbox/...`, the clone has
> no remote-tracking ref for the sandbox branch. The explicit refspec in the first line above
> creates it; a bare `git fetch origin sandbox/...` only writes `FETCH_HEAD`.

## 🚧 The Boundary Rule

> **Rust is not here to make `join()` faster.** It is here to make large-scale filesystem
> operations fast and memory-efficient.

This is the decision that makes the native dependency justified rather than decorative, and
it is enforced in review. An N-API round trip costs ~500–2000 ns; `pathe` does the same
string work in ~50 ns.

| Tier | Crosses the boundary | Why |
|------|----------------------|-----|
| **A** | `walk()`, `hashTree()`, `copyTo()`, `snapshot()` | One call replaces 100k+ JS↔libuv round trips |
| **B** | `read()`/`write()` with a native codec, `hash()` | Once per file, where I/O dominates the hop |
| **C** | `withLock()`, `temp()`, `watch()` | `flock()`, `O_TMPFILE`, `inotify` — unreachable from JS |
| **—** | `join`, `resolve`, `dirname`, `basename`, `normalize` | **Never.** `pathe`, in TypeScript |

Rejected on the record: WASM/WASI (a filesystem library needs real OS access) and `bun:ffi`
(experimental, and it would lock the package to one runtime). See
[`.knowledge/architecture/napi-boundary.md`](.knowledge/architecture/napi-boundary.md).

## 🏗️ Repository Architecture

| Path | Description |
|------|-------------|
| `crates/core` | `pathway-fs-core` — rlib, **all** engine logic, zero napi dependencies; the whole test story runs without Node |
| `crates/path` | `pathway-fs` — the ergonomic pathlib-like Rust surface over core (v0.3 preview) |
| `crates/engine` | `pathway-fs-engine` — cdylib NAPI-RS bridge, glue only; npm-only, never on crates.io |
| `crates/package.json` | The Cargo workspace as **one** turbo package (`@repo/rust`); cargo locks `target/`, so per-crate packages would serialise on it |
| `packages/path` | `@archont561/pathway` — the published TypeScript surface; `napi.binaryName = "pathway"` |
| `packages/typescript-config` | `@repo/typescript-config` — shared tsconfig, internal by convention, never published |
| `apps/docs` | Astro + Starlight docs site → <https://archont561.github.io/pathway/> |
| `.knowledge/` | Open Knowledge Format v0.2 bundle: decisions D1–D7, architecture, features, competitive analysis |
| `backlog/` | Markdown backlog: 4 milestones, 27 tasks, and the delivery docs (phase plan, roadmap, success metrics) |
| `.github/workflows/ci.yml` | Three caches and one command: `pixi run ci` |
| `.github/workflows/docs.yml` | Pages publish, gated on `workflow_run` of a green ci |
| `.github/workflows/publish-sandbox.yml` | Packs and publishes the offline transport branch |
| `.pixi-sandbox.toml` | The reviewed publish plan: bundles, platforms, branch prefix, cargo vendoring |
| `scripts/restore.sh` | One-command offline reconstruction; branch derived from the same plan |
| `lefthook.yml` | Git hooks — every hook calls a pixi task, so hooks and CI cannot drift |
| `.devcontainer/` | Official pixi image, `git`/`gh` as pixi globals, opencode installed by `setup.sh` |
| `deny.toml` | cargo-deny policy: licences, bans, sources |

## 🛠️ Development & Quality Gates

Pixi exposes **repo-wide verbs only**. Each one is `turbo run <verb>` over every package that
implements it, so a verb spans both languages and you never have to think about which half of
the repo a check belongs to. `pixi.toml` contains no `cargo`, `tsc`, `astro` or `biome`
invocation at all.

| Command | What it does |
|---------|--------------|
| `pixi run lint` | `cargo fmt --check`, `clippy -D warnings`, `cargo deny` (licences/bans/sources), biome, actionlint |
| `pixi run test` | `cargo nextest` over the workspace, the Rust doctests, and the Bun suites |
| `pixi run typecheck` | `tsc --noEmit` and `astro check` |
| `pixi run gates` | The three above — everything that must pass before a push |
| `pixi run coverage` | Rust coverage via `cargo-llvm-cov`, written to `crates/lcov.info` |
| `pixi run ci` | `gates` plus coverage and the release and production builds: exactly what CI runs |
| `pixi run fmt` | Rewrite sources with rustfmt and biome |
| `pixi run lint-advisories` | The RustSec advisory check. Needs the network, so it is CI-only and outside `lint` |
| `pixi run backlog` / `skills` | The Markdown backlog and the agent-skills CLI |
| `pixi run sandbox-{plan,pack,doctor,publish,restore}` | The offline transport pipeline |

`deny.toml` is the gate behind the crates.io decision: two of the three crates are meant to be
published, so a non-permissive or unmaintained licence has to fail a gate rather than be
discovered by a consumer.

### Reaching one package

The commands live in the package that owns them; pixi does not re-export them. To run one
directly, filter the same turbo graph:

```bash
turbo run lint --filter=@repo/rust     # just the Rust gate
bun run docs:dev                       # just the docs site
bun run --cwd crates coverage:report   # just the coverage summary
```

Because it is one graph, `pixi run build` and `bun run docs:build` share a task **and a cache
entry** rather than being two ways to build the same site.

### Dev container

`.devcontainer/devcontainer.json` is seven keys and no Dockerfile — it runs the official
`ghcr.io/prefix-dev/pixi` image as-is. That image is Ubuntu plus the pixi binary: no `git`,
no C compiler. So the post-create step delegates to a commented script,
`.devcontainer/setup.sh`, which provisions in dependency order:

1. **Host tools** — `git`/`gh` as pixi globals (Source Control, lefthook, `scripts/restore.sh`) plus a C toolchain, because `blake3-sys` shells out to `cc`/`ar` from its build script and without one `cargo build` cannot compile at all.
2. **Environments** — `pixi install --locked --all`, which fails rather than re-solving, so the container cannot drift from the `pixi.lock` the sandbox branch is built from.
3. **Bun workspace** — through a pixi task, not a bare `bun install`: `bun` lives in the materialised environment, which is on `PATH` inside a task and nowhere else.
4. **opencode** — the agent CLI, installed last because it needs bun from step 3.

opencode is installed with a global `bun install` into `$HOME/.bun` and added to `.bashrc`,
which keeps it on `PATH` for ordinary shells rather than only inside `pixi run`. It is
**deliberately not a pixi task**: `pixi.toml` describes what the repository is built, tested
and released with, and a ~185 MB agent binary is none of those. Keeping it out also keeps it
out of the packed sandbox branch, which would otherwise carry the blob to an airlock with no
use for it.

### Bun workspace

The root `package.json` makes this one bun workspace over `packages/*`, `apps/*` and `crates`,
with a single `bun.lock` hoisted into the root `node_modules`. There is **no Node.js anywhere**
in `pixi.toml`: `bun` is the only JavaScript runtime, and it carries turbo, biome, `backlog.md`
and `skills` as workspace packages rather than conda dependencies — conda-forge has no `turbo`,
and biome is resolved from `package.json` so one lockfile decides both the linter and the
version its `biome.json` schema names. Tasks therefore reach the JS toolchain through
`bun x` / `bun run` and never through a `node_modules/.bin` path, whose entries carry a `node`
shebang that no environment here provides.

`convco`, `lefthook` and `actionlint` *are* conda dependencies, because the git hooks must work
on a machine restored from the sandbox branch, where a restored `default` environment's `bin/`
is on `PATH` but no `node_modules` exists.

## 📂 The Transport Layout

```text
sandbox/developer-linux-64/      # orphan branch, published by publish-sandbox.yml
├── .pixi-sandbox/
│   ├── manifest.json            # SHA-256 catalog, source commit, tool versions
│   ├── envs/default/pack/       # conda packages + env.yml
│   ├── tools/linux-64/          # pixi, pixi-unpack, pixi-sandbox (static, verified)
│   └── vendor/                  # cargo vendor --versioned-dirs (100 crates, loose)
└── README.md / AGENTS.md        # restore instructions, for humans and agents
```

`.pixi-sandbox.toml` is the reviewed plan — one `developer` bundle over the `default`
environment on `linux-64`, with `cargo_vendor = true` — and `pixi run lint-sandbox-plan`
fails if what is published and what the restore script looks for ever disagree.

## 🔖 Changelog & Release

- **Changelog** — `CHANGELOG.md` is generated from conventional commits by `pixi run changelog` ([convco](https://convco.github.io/)); `pixi run changelog-preview` prints without writing. `pixi run lint-commit` is a gate, because a message that does not parse is a changelog entry that silently disappears.
- **Versions** — `[workspace.package] version` in the root `Cargo.toml` is the single source. `scripts/version.ts` carries it to the docs site, and a test asserts `packages/path/package.json` agrees, so the published surfaces cannot drift.
- **Publishing** — not yet. All three crates are `publish = false` until the crates.io names are reserved; the npm platform matrix is generated by `napi publish` when that lands.
